# Generated device communication tests — design

## Intent

The integrator of a new LE device is Claude. With `python -m lecore new-device` it gets a device class
(`ModbusDev` / `LeBinDev` subclass) with the communication API, but it has to invent the hardware tests of that
API again for every device. Existing device tests (`tests/test_rftb_mb.py`, `tests/test_rftb_lebin.py`) are
nearly identical hand-written copies and cover no error states.

Goal: lecore ships a reusable pytest test suite for device communication, and `new-device` generates a small test
file next to the device class that only plugs the device into it. Fixes and new tests then come with a lecore
update, the generated files stay untouched.

## Goals

- Pytest tests of communication with a **real device**, real register map and real firmware binary.
- Coverage: write with read-back, single read, read of all registers, read of a register known to the map but
  unknown to the device, other error states (below), firmware upgrade.
- Generated by `new-device`: `test_modbus.py` for the Modbus class, `test_lebin.py` for the LeBin class, each only
  when that class is generated in the run (dual-protocol directory → both files).
- One clearly marked configuration place in the generated file; default device is the generated class, with an
  entry point for an exact definition (another class or a factory returning an opened device).
- Works as a part of a larger suite: plain pytest, collected by a global runner in a parent directory which writes
  results with `--junitxml`.

## Non-goals

- No own result storage or reporting (no `xmlrunner`, no `test-reports/`); the global runner owns that.
- No simulated device / CI run of the device tests themselves.
- No device-specific functional tests (measurement accuracy etc.); only the communication API.
- Not replacing `TestFrame` (`CoreTest`, `Runner`); it stays as is.
- No visual (GUI/TUI) tests.

## Anti-goals

- Tests must not silently pass or skip on a device that does not communicate: if the device cannot be opened or
  does not answer, tests fail.
- Tests must not write to registers other than the configured test register (a real device may be connected to
  real equipment).
- Generated test file must not be overwritten on a regenerate without `force` (it holds the integrator's
  configuration), same as the device modules.

## Constraints

- Tests are pytest-style (not `unittest`), lecore must not get a runtime dependency on pytest: the suite module
  imports pytest, it is only imported by the generated tests.
- Python 3.9+, pymodbus 2.x and 3.x (via existing `MbClient` helpers).
- `Scaffold.py` must not import the Modbus/LeBin stack (existing rule); the generated file imports the suite only
  at test time.
- Device API as it is: `read(name)` returns `None` on communication error, `write()` returns `0` (Modbus) /
  `True` (LeBin) on success and `None` on error, local validation raises `KeyError`/`ValueError`/`TypeError`
  (`Devices/Validation.py`). `Modbus RegMap` retries a failed request (`attempts=2`, `delay=0.5`).

## Design (decided)

### Suite in lecore

New module `lecore.testing` (exact module name is the builder's call) with two base classes, e.g.
`ModbusDeviceTests` and `LeBinDeviceTests`, sharing a common part. Names must not start with `Test`, so pytest does
not collect the bases themselves.

The device is opened once per test class (class-scoped fixture) and closed at the end.

Configuration as class attributes of the subclass in the generated file:

| Attribute | Meaning | Default |
|-----------|---------|---------|
| `device_class` | device class to instantiate | generated class |
| `open_kwargs` | arguments of `open()` (comport, slave, baud rate, ...) | `{}` → `ComSettings*.json`, LeBin USB search when `usb` is declared |
| `create_device()` | classmethod entry point returning an **opened** device; overriding it replaces `device_class` + `open_kwargs` | instantiate `device_class`, `open(**open_kwargs)` |
| `test_register` | register safe to write (read-back test) | `None` → write test skipped with a reason |
| `exclude` | register names not to be read in the read-all test | `[]` |
| `unknown_address` / `unknown_id` | Modbus address / LeBin ID not supported by the device | protocol-specific default chosen by the builder |
| `wrong_slave` (Modbus) | slave address with no device on the bus | some unused address, e.g. 247 |
| `firmware` | firmware binary for the upgrade test | `None` → upgrade test skipped with a reason |
| `reboot_time` | wait after upgrade | 5 s |

### Tests

Order matters only for the upgrade, which runs last.

1. **Read** — a register (first readable one, or `test_register` when set) is read, result is not `None`.
2. **Write with read-back** — a random valid value (respecting format, Min/Max, enumeration) is written to
   `test_register`, read back and compared. The original value is restored afterwards.
3. **Read all** — every register of the map except `exclude` is read; all failures (`None`) are collected and
   reported at once in one assertion message.
4. **Unknown register** — a register with `unknown_address` / `unknown_id` is injected into the loaded register
   map **in memory only** (copy of an existing register definition with changed address/ID and a unique name),
   read through the public `read()`. Expected: returns `None`, no exception. If the device answers with data,
   the test fails with a hint to set `unknown_address` / `unknown_id`. The injected register is removed afterwards.
5. **Wrong slave (Modbus only)** — read with `wrong_slave` returns `None` within the timeout; the original slave
   is restored.
6. **Locally rejected writes** — writing a read-only register and a value outside Min/Max raises `ValueError`.
   Uses a suitable register from the map; skipped with a reason when the map has none. Nothing is sent to the
   device (no device state is changed).
7. **Recovery after error** — after each error test (4, 5) a normal read succeeds (part of those tests, so a
   failure points at the error state that broke communication).
8. **Close and reopen** — `close()`, then reopen with the same configuration, a read succeeds.
9. **Firmware upgrade** — `upgrade_firmware(firmware, reboot_time)` returns success, then a read succeeds.

### Generated files

`new-device` writes next to the device module:

- `test_modbus.py` when a Modbus class is generated, `test_lebin.py` when a LeBin class is generated.
- Content: imports of the suite base and the device class (+ `Reg` constants), one subclass `Test<Device>` with
  the configuration attributes pre-filled from what the generator knows (class, register map, USB id) and the
  rest commented with explanation (`test_register`, `firmware`, ...). A short module docstring says how to run it
  (`pytest <dir>` / from the global runner with `--junitxml`).
- Existing test files are kept unless `force`; the result dictionary reports them like other files
  (`created` / `overwritten` / `kept`).
- For already existing devices a separate command `python -m lecore new-tests` (API `lecore.generate_tests()`)
  creates only the missing `test_modbus.py` / `test_lebin.py` for the device classes found in the directory;
  existing test files are kept unless `force`. Device modules and configuration files are not touched.

### Marker `hardware`

All suite tests carry the pytest marker `hardware`, so a run without devices deselects them with
`-m "not hardware"`. Without deselecting they fail when no device answers (no silent skip). The marker must be
registered wherever the tests are collected (no unknown-marker warning in the global runner), e.g. by a pytest
plugin entry point (`pytest11`) of lecore; the mechanism is the builder's call.

### Documentation

- Generated `CLAUDE.md` of the device package: a paragraph on how to fill in and run the tests.
- `src/lecore/QUICKSTART.md` and `doc/new-device.md` (kept in sync per project rules): the test suite, its
  configuration and the generated files.
- `README.md` only links to the documentation, per repository rules.

### Testing of the feature itself (no hardware)

- `tests/test_scaffold.py`: generation of `test_modbus.py` / `test_lebin.py` for Modbus, LeBin and dual
  directories by `new-device` and `new-tests`, keep/overwrite with `force`, generated file compiles and imports.
- Suite logic is covered by a hardware-free test with a stub device (e.g. a device opened with an external fake
  `client`) where practical; added to the CI test list.
- Real hardware verification on an available device (RFTB Modbus and LeBin) before release.

## Calls made by the designer (not discussed with the owner)

- `create_device()` returns an opened device; close-and-reopen (test 8) and slave restore (test 5) use
  `device.close()` / `device.open()` without arguments, relying on `open()` keeping its settings in the instance
  (`mb.s`, `com`, `slave`). A factory must therefore apply its port settings through `open()`.
- Test 6 (locally rejected writes) never touches the real port: the device temporarily gets a stub `client`
  (`open(client=stub)`, original restored afterwards) recording sent requests, and the test asserts `ValueError`
  **and** nothing sent. So it may use
  any read-only / Min-Max register of the map without risk to the hardware.
- Dual-protocol devices: `test_modbus.py` and `test_lebin.py` are independent, each opens and closes its own
  connection and has its own `firmware` setting (default `None`). Upgrade runs last within its class only; the
  generated comment recommends enabling the upgrade in one of the files.

## Left to the builder

- Module and class names of the suite, fixture mechanics, how the injected register is added/removed for each
  protocol.
- Default `unknown_address` / `unknown_id` values and how a random valid value is generated per format.
- Whether existing `tests/test_rftb_*.py` are migrated to the suite (nice to have, not required).
- Exact wording and layout of the generated file and docs.
